Да. Я бы **переходил на одно основное локальное название для каждой географической сущности**, а не хранил `name_en / name_ru / name_uk` для всех стран подряд.

Например:

```text
Украина → Київ, Львів, Запоріжжя
Россия → Москва, Казань
Польша → Warszawa, Kraków
Чехия → Praha, Brno
Германия → Berlin, München
```

То есть язык интерфейса сайта больше не определяет язык названия города.

Вместо:

```python
name_en
name_ru
name_uk
```

делать условно:

```python
name
ascii_name
```

А у страны хранить язык, из которого импортёр берёт основное название:

```text
UA -> uk
RU -> ru
PL -> pl
CZ -> cs
DE -> de
```

Например поле:

```python
geo_locale
```

или:

```python
preferred_name_language
```

Но не `official_language`, потому что есть страны с несколькими официальными языками.

Единственное, что я бы не выкидывал полностью — **альтернативные названия для поиска**.

Например основное имя:

```text
Київ
```

но пользователь может искать:

```text
Киев
Kyiv
Kiev
```

Поэтому можно позже иметь отдельные алиасы:

```python
class CityAlias(models.Model):
    city = models.ForeignKey(City, on_delete=models.CASCADE)
    name = models.CharField(max_length=255)
    language_code = models.CharField(max_length=10, blank=True)
```

Но эти алиасы нужны **для поиска**, а не для отображения.

И да: текущая логика сайта не обязательно развалится. Старый метод можно временно оставить:

```python
def get_name(self, language=None):
    return self.name
```

Тогда существующий код продолжит работать, а зависимость от `name_ru / name_uk / name_en` можно вычищать постепенно.

Итого: **идея правильная — хранить локальное название страны/города, а языки интерфейса отделить от GEO вообще.** Это будет проще, чище и меньше мусора в базе.

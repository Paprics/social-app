# Цель документа

Ответить на вопрос:

> **Какие сущности есть в messenger и как они связаны между собой?**

Без единой строки Django-кода.

---

# Что должно быть в документе

## 1. Список сущностей

На текущем этапе достаточно четырех:

* Dialog
* Participant
* Message
* Attachment

Никаких лишних сущностей "на будущее". Если через полгода понадобится реакция на сообщения (`Reaction`) или удаление сообщений для себя (`MessageState`) — добавим тогда.

---

## 2. Связи

Например, в виде простой схемы:

```text
User
 │
 ├──────────────┐
 │              │
 ▼              ▼
Participant   Message
 │              │
 └──────► Dialog ◄────── Attachment
```

Или чуть подробнее:

```text
User
  │
  │ 1:N
  ▼
Participant
  │
  │ N:1
  ▼
Dialog
  │
  ├───────────┐
  │           │
  ▼           ▼
Message   Attachment
```

---

## 3. Каждая модель

Не код.

А описание.

Например.

### Dialog

Назначение

Хранит информацию о диалоге.

Ответственность

* идентификатор
* дата создания
* тип диалога
* последнее сообщение

Не хранит список пользователей.

Это делает Participant.

---

### Participant

Назначение

Связывает пользователя и диалог.

Ответственность

* пользователь
* диалог
* дата входа
* последнее прочитанное сообщение
* архивирован ли диалог
* заглушен ли диалог

---

### Message

Назначение

Одно сообщение.

Ответственность

* автор
* текст
* время
* удалено
* изменено

---

### Attachment

Назначение

Файл сообщения.

Ответственность

* файл
* тип
* размер
* message FK

---

## 5. Ограничения

Например

Participant

```
(dialog, user)
```

должно быть уникальным.

---

Message

Нельзя без автора.

---

Attachment

Нельзя без сообщения.

---

Dialog

Минимум два участника.

(Это уже правило сервиса, а не ограничение БД. Такие вещи тоже полезно зафиксировать.)

Пока просто список.

```

Participant

```

Attachment

```

```

## Почему именно сейчас

До этого мы определили **архитектуру приложения**. Теперь определяем **архитектуру данных**. После этого писать Django-модели станет почти механической задачей: мы не будем придумывать поля "на лету", а просто реализуем уже утвержденную схему.

### Я бы предложил немного изменить общий порядок работ

Вместо:

1. Архитектура
2. База данных
3. Код моделей

Я бы добавил еще один обязательный этап:

1. ✅ `001_architecture.md`
2. ✅ `002_database.md`
3. ✅ `005_services.md`
4. **Только потом** писать модели.

Причина простая: именно сервисы диктуют, какие поля действительно нужны моделям. Например, если `MessageService` должен быстро показывать список диалогов с последним сообщением, мы можем заранее решить, нужен ли `Dialog.last_message`. Если сначала написать модели, а потом проектировать сервисы, часто приходится возвращаться и переделывать схему БД.

То есть сейчас я бы не спешил открывать `models/dialog.py`. Сначала стоит закончить проектирование, чтобы реализация стала последовательной, а не итеративной. Это обычно окупается уже на первых нескольких фичах.

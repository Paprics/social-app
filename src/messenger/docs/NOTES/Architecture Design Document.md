# Architecture Design Document

## Messenger App

### Назначение

Messenger — отдельное приложение Django, реализующее систему личных сообщений в режиме реального времени.

Первоначально приложение должно поддерживать исключительно личные диалоги (1-to-1), однако вся архитектура проектируется таким образом, чтобы в дальнейшем без изменения моделей данных и без крупных рефакторингов можно было добавить:

* групповые чаты;
* публичные комнаты;
* каналы;
* пересылку сообщений;
* вложения (изображения, документы и т.п.);
* реакции;
* ответы на сообщения;
* закреплённые сообщения;
* модерацию;
* роли участников.

Иными словами, MVP реализует только личную переписку, однако структура приложения сразу соответствует архитектуре полноценного современного мессенджера.

---

# Используемый стек

Проект уже использует:

* Python 3.12
* Django 5.x
* PostgreSQL
* Redis
* Django Channels
* ASGI
* HTMX
* Tailwind CSS
* Celery

Повторно использовать уже существующую инфраструктуру проекта.

Не создавать альтернативных механизмов работы с Redis, WebSocket и ASGI.

Все новые компоненты должны интегрироваться в существующую архитектуру проекта.

---

# Основные требования

Мессенджер должен работать максимально близко к современным приложениям (Telegram, Messenger, Discord), а не по схеме классических сайтов начала 2000-х.

Пользователь не должен обновлять страницу для получения новых сообщений.

Все изменения должны приходить автоматически.

---

# Способ обмена данными

Использовать два механизма одновременно.

## HTMX

Используется для обычных HTTP-запросов:

* открытие страницы мессенджера;
* получение списка диалогов;
* создание нового диалога;
* поиск пользователей;
* поиск диалогов;
* первоначальный рендер;
* подгрузка старых сообщений;
* пагинация.

---

## Django Channels + WebSocket

Используется исключительно для событий реального времени.

Например:

* новое сообщение;
* пользователь печатает;
* сообщение прочитано;
* пользователь появился онлайн;
* пользователь вышел офлайн;
* изменение списка диалогов;
* изменение последнего сообщения;
* обновление количества непрочитанных сообщений.

WebSocket не должен использоваться вместо обычного HTTP там, где это не требуется.

---

# Redis

Redis используется как транспорт событий и кэш.

Использовать существующий Redis проекта.

В Redis хранить только краткоживущие данные.

Например:

* typing;
* online presence;
* websocket channels;
* временные служебные структуры.

Redis не должен становиться постоянным хранилищем сообщений.

Все сообщения должны храниться исключительно в PostgreSQL.

---

# PostgreSQL

PostgreSQL является единственным постоянным источником данных.

Хранятся:

* диалоги;
* участники;
* сообщения;
* вложения;
* статусы сообщений;
* время прочтения;
* системные данные.

---

# Архитектура хранения

Основные сущности.

Dialog

Контейнер переписки.

Не зависит от количества участников.

Даже если сейчас существует только личный диалог, модель должна поддерживать возможность появления групповых чатов без изменения схемы.

---

Participant

Связующая модель между пользователем и диалогом.

Хранит индивидуальное состояние пользователя относительно конкретного диалога.

В дальнейшем здесь могут находиться:

* архивирован;
* закреплён;
* muted;
* удалён только для себя;
* последнее прочитанное сообщение;
* счётчик непрочитанных;
* пользовательские настройки диалога.

Использование отдельной модели Participant обязательно.

Нельзя хранить участников напрямую в Dialog.

---

Message

Хранит сообщение.

На первом этапе:

* текст;
* автор;
* дата создания;
* дата редактирования;
* статус удаления.

Архитектура должна предусматривать возможность появления вложений.

---

Attachment

На MVP может не использоваться.

Но модель должна существовать.

В дальнейшем через неё будут подключаться:

* изображения;
* документы;
* видео;
* аудио.

Никаких изменений моделей Message при этом происходить не должно.

---

# Прочитанные сообщения

Система должна поддерживать статус прочтения.

Использовать хранение последнего прочитанного сообщения участником диалога.

Не хранить отдельную запись "прочитано" для каждого сообщения.

Такой подход значительно масштабируемее.

На основании последнего прочитанного сообщения вычисляются:

* количество непрочитанных;
* статус "прочитано";
* статус "доставлено".

---

# Typing

Состояние "печатает" хранится исключительно в Redis.

Не записывается в PostgreSQL.

Передаётся только через WebSocket.

После истечения TTL автоматически исчезает.

---

# Online

Онлайн хранится аналогично текущей архитектуре проекта.

Использовать существующие сервисы определения online.

Не создавать вторую систему online.

---

# Обновление интерфейса

После открытия диалога пользователь больше не обновляет страницу.

Новые сообщения появляются автоматически.

Последнее сообщение в списке диалогов обновляется автоматически.

Количество непрочитанных обновляется автоматически.

Статусы прочтения обновляются автоматически.

Статус "печатает..." обновляется автоматически.

---

# Масштабируемость

Архитектура должна позволять без изменения существующих моделей добавить:

* изображения;
* документы;
* групповые чаты;
* публичные комнаты;
* реакции;
* ответы;
* закрепление сообщений;
* пересылку сообщений;
* голосовые сообщения;
* поиск по сообщениям.

Все эти функции должны добавляться расширением существующей архитектуры, а не её переписыванием.

---

# Архитектура приложения

Использовать разделение ответственности.

models

Хранят исключительно структуру данных.

Без бизнес-логики.

---

repositories

Работают исключительно с базой данных.

Создание.

Обновление.

Удаление.

Массовые операции.

---

selectors

Содержат сложные запросы.

Используются для получения данных.

Например:

* список диалогов;
* поиск сообщений;
* поиск пользователей;
* непрочитанные сообщения.

---

services

Содержат бизнес-логику.

Например:

* отправить сообщение;
* создать диалог;
* отметить прочитанным;
* начать печатать;
* закончить печатать.

Не должны содержать SQL-запросов.

---

consumers

Работают только с WebSocket.

Максимально тонкие.

Основная логика должна находиться в сервисах.

Consumer только принимает событие и передаёт его дальше.

---

views

Используются только для HTTP и HTMX.

Без логики WebSocket.

---

# Производительность

Максимально использовать:

select_related()

prefetch_related()

bulk_create()

bulk_update()

Минимизировать количество SQL-запросов.

Избегать N+1.

---

# Celery

Celery использовать только для тяжёлых фоновых задач.

Например:

* очистка старых вложений;
* пересоздание поискового индекса;
* генерация превью изображений;
* длительные фоновые операции.

Отправка обычного сообщения не должна проходить через Celery.

---

# Принципы реализации

* разделение ответственности;
* минимальная связанность компонентов;
* высокая расширяемость;
* отсутствие дублирования логики;
* повторное использование существующей инфраструктуры проекта;
* возможность постепенного расширения функциональности без изменения архитектуры.

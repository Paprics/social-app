## 2. Основные принципы

Здесь фиксируем правила.

Например:

* Messenger — самостоятельное приложение Django.
* Бизнес-логика находится только в services.
* Selectors отвечают только за чтение данных.
* Models не содержат бизнес-логики.
* Consumers не принимают решений.
* Views не работают с ORM напрямую.
* Любое изменение данных проходит через Service.
* WebSocket используется только для событий реального времени.
* История сообщений загружается по HTTP.

Это становится "конституцией" модуля.

# 3. Архитектурные принципы

Это очень важный раздел.

Например:

### View

Отвечает только за HTTP.

Никакой бизнес-логики.

---

### Consumer

Отвечает только за WebSocket.

Получил JSON.

Проверил.

Передал сервису.

Отправил ответ.

---

### Service

Главный слой бизнес-логики.

Именно здесь принимаются все решения.

---

### Selector

Только чтение.

Сложные SELECT-запросы.

Никаких UPDATE.

---

### Repository

⚠️ Здесь я предлагаю остановиться и принять решение.

После обсуждения с другим ИИ я тоже считаю, что **Repository не стоит вводить "на всякий случай"**.

Для Django это действительно нетипичный слой.

Есть три варианта:

### Вариант А (мой фаворит)

```
View
Consumer
      │
      ▼
 Service
      │
 ┌────┴────┐
 ▼         ▼
Selector  ORM
```

То есть сервис сам использует ORM для создания, изменения и удаления объектов, а селекторы отвечают только за сложное чтение.

Это соответствует практике многих Django-проектов (в том числе подходам HackSoft).

---

### Вариант B

```
Service

↓

Repository

↓

ORM
```

Классический Repository Pattern.

Полезен, если предполагается смена ORM или нескольких источников данных, но для твоего проекта это, скорее всего, лишняя абстракция.

---

Я бы **пока отказался от Repository**. Если через год появится реальная потребность, его можно ввести. Удалить ненужный слой потом сложнее, чем добавить.

# Что я бы ещё добавил

Есть один принцип, который сильно поможет именно твоему проекту.

## Компонентная изоляция

Каждое приложение должно вести себя так, словно оно может быть вынесено в отдельный пакет.

Это означает:

* приложение само содержит свои модели, сервисы, селекторы, тесты и документацию;
* другие приложения взаимодействуют с ним только через публичные сервисы или чётко определённые точки интеграции;
* минимизируется количество прямых импортов внутренних модулей.

Это сделает архитектуру чище и облегчит дальнейшее развитие.
